### 1.2 Java حسب الإصدار
`≤1.16 → 8` · `1.17 → 16` · `1.18–1.20.4 → 17` · `1.20.5+ / 1.21.x → 21` · `26.x → 25`
تأتي الأولوية لـ`javaVersion` من Mojang عند توفره، والمصفوفة أعلاه احتياطية.

### 1.3 Playit.gg
- الوكيل الرسمي: `playit-cloud/playit-agent` إصدار `v1.0.10` مع أصل `playit-linux-amd64`.
- المصادقة: متغير `SECRET_KEY` (أو `--secret`).
- **لا توجد واجهة عامة لإنشاء الأنفاق تلقائياً** → التطبيق يرشد المستخدم، يخزّن المفتاح مشفراً، ويثبّته كـGitHub Secret. العنوان العام يُقرأ من سجل الوكيل، ولا يُكتب يدوياً.

### 1.4 GitHub Actions
- `if: env.X` لا يرى القيم المكتوبة في `$GITHUB_ENV` من خطوة سابقة → استُبدل بمخرجات خطوات.
- الحد الأقصى 6 ساعات؛ الدورة تضبط `timeout-minutes: 330` لتبقى مساحة للنسخ الاحتياطي وإعادة التشغيل.
- `actions/cache` للاستعادة السريعة + Release asset للنسخة الدائمة.

## 2. ما تغيّر فعلياً / What actually changed

### 2.1 التدفق الأول (First run)
`Splash → GitHub Device Flow → Playit.gg → إنشاء أول سيرفر → التطبيق`
- لا شريط تنقل قبل وجود سيرفر حقيقي.
- لا تُطلب كلمة مرور GitHub إطلاقاً (Device Flow فقط).
- لا يُعلَن أن Playit «مرتبط» قبل أن يثبت تشغيل حقيقي أن النفق متصل.

### 2.2 التنقل: خمسة أقسام فقط
`الرئيسية` · `الكونسول` · `الملفات` · `المودات` · `إعدادات السيرفر`
كل ما تبقّى (السيرفرات، النسخ الاحتياطي، العوالم، الشبكة، الحساب، إعدادات التطبيق) صار صفحات داخلية.

### 2.3 محرّك التشغيل الحقيقي
- `nova-craft/runner.sh` + `nova-craft/config.py` + `.github/workflows/novacraft-server.yml`.
- تنزيل حقيقي مع تحقق SHA-256 / SHA-1 / MD5، و`server.jar` يُعاد تنزيله إذا فشل التحقق.
- `eula.txt` يُكتب **فقط** عندما يختار المستخدم الموافقة؛ وإلا يُحذف ويُرفض التشغيل برسالة واضحة.
- انتظار جاهزية حقيقي (`Done (Xs)!` / `Server started`) وليس نجاح Actions.
- `status.json`: الطور، الجاهزية، اللاعبون، الذاكرة، حالة النفق، **عنوان النفق المُبلَّغ**.
- `live.log`: آخر ‎~260‎ سطراً من سجل السيرفر، والكونسول يعرضه بوسم **Polling** لا Live.
- إيقاف آمن: `save-off` → `save-all flush` → نسخة مضغوطة + SHA-256 → `stop`.
- استعادة من أحدث Release `backup-<id>-*` أو من `restore_tag` محدد.
- استيراد عالم من `nova-craft/import/world.zip` ثم حذف الملف من المستودع.
- إعادة تشغيل تلقائية بدورة جديدة إلى أن يصل الحد الزمني أو يُطلب الإيقاف.

### 2.4 الملفات
- متصفح الملفات مقيّد بـ`server/` (أو `dataPath`): لا يمكن عرض أو فتح أو كتابة أي ملف من المستودع.
- تحقق احتواء المسار قبل كل تنقل/إنشاء/رفع.
- إنشاء/تحرير/حذف مع تأكيد، ورفع حتى 30MB.

### 2.5 المودات
- تبويب Mods (Fabric/Quilt) وPlugins (Paper/Purpur/Spigot/Bukkit).
- فلترة Modrinth حسب loader + إصدار اللعبة عبر عقد واحد (`modrinthCompatible`) يشاركه الاختبار والشاشة.
- رفض غير المتوافق برسالة تذكر loader/الإصدار المطلوب مقابل المتوفر، ولا يُنزَّل الملف أصلاً.
- مجلد التثبيت `server/mods` أو `server/plugins` مشتق من `serverRoot` (يدعم `dataPath` المخصص).

## 4. الأمان / Security
- لا مفاتيح أو كلمات مرور في المستودع أو الكود.
- أسرار GitHub في `flutter_secure_storage` (Keystore) وليست في `SharedPreferences`.
- السر يُثبَّت كـActions secret فقط، ولا يُطبع في السجلات (`set -x` ممنوع، والاختبار يتحقق من ذلك).
- عمليات الحذف/الاستبدال تتطلب تأكيداً.
- أقل الصلاحيات: `contents: write` + `actions: write` فقط لسيرفر المستودع.

### 5.2 ما تم التحقق منه فعليًا
- GitHub Device Flow: طلب رمز جهاز حقيقي من `github.com/login/device/code` بالمعرّف `Iv23linL1Tf6ResSgUqL` → HTTP 200 مع `user_code` (أي أن Device Flow مُفعّل للتطبيق).
- صلاحيات تطبيق GitHub عبر API: `actions:write`, `contents:write`, `metadata:read`, `repository_creation:write`, `secrets:write`, `workflows:write`.
- Bedrock: استجابة Mojang الرسمية تحتوي `serverBedrockLinux` للإصدار `1.26.52.3`.
- `fileops.py`: manifest + snapshot/apply-snapshot + كتابة/حذف/إعادة تسمية داخل الجذر فقط؛ `../../etc/passwd` → `path-outside-root`؛ مدخل ZIP خارجي → `unsafe-archive-entry`؛ استيراد عالم فعلي نجح.
- `playit.py`: قراءة rundata (Java/Bedrock)، رفض مفتاح غير صالح، وبناء طلب إنشاء النفق.
- تثبيت حزم `.mcaddon`: فُكّت حزمة بمجموعتَي behavior/resource وتمت كتابة `world_behavior_packs.json` و`world_resource_packs.json` فعليًا.
- اختبارات جديدة (GitHub API عبر MockClient): الفرع الافتراضي، `dispatch ref`، تغليف السر والتحقق منه، ورفض الكتابة غير المؤكدة.

## 4. إصلاح انهيار الإقلاع على الجهاز الحقيقي

**العَرَض:** نسخة `39058403987` تُظهر شاشة البداية ثم تُغلق فوراً وتعود إلى الشاشة الرئيسية.

### ما تم إثباته بالأدلة (وليس بالافتراض)
1. **التوقيع ليس سبب الانهيار.** `apksigner verify --verbose` على الملف المنشور نفسه يقول
   `Verifies` مع v2 صالح. تحذير MT Manager («Verified failed») ظهر لأن APK كان يحمل **v2 فقط**
   بلا توقيع JAR/v1، وهو تحذير أدوات لا سبب لإنهاء العملية. أُضيف الآن v1+v2+v3.
2. **ليس مشكلة صفحة 16KB.** فحص `readelf -lW` داخل CI لكل `lib/*.so` أظهر محاذاة LOAD
   `0x4000` أو `0x10000` (المطلوب 2^14)، أي أن النسخة متوافقة مع أجهزة Android 15/16 ذات صفحة 16KB.
3. **ليس مشكلة ABI.** حزمة arm64 تحتوي `arm64-v8a` فقط وهي الصحيحة للهاتف.
4. **التطبيق سليم عند الإقلاع في بيئة اختبار حقيقية (محاكي API 30):** تثبيت ناجح،
   `am start -W` → `Status: ok`, `LaunchState: COLD`, `Displayed ... +1s108ms`، والعملية
   ما زالت حيّة بعد 15 ثانية. الدليل في تعليق الالتزام `e63ad4b` وفي artifact
   `android-smoke-39065318083`.

### التغيير السلوكي الوحيد الموجّه للانهيار
- **إيقاف Impeller** عبر `io.flutter.embedding.android.EnableImpeller=false` في
  `AndroidManifest.xml`. Flutter 3.35 يفعّل Impeller افتراضياً، وفيه انهيارات SIGSEGV/SIGABRT
  موثّقة على بعض معالجات Mali/Adreno تحدث **بعد** ظهور شاشة البداية بالضبط
  (flutter#175562، flutter#190195). التطبيق واجهة إدارة، فالأولوية للاستقرار على حساب
  محرك الرسم الافتراضي؛ Skia يبقى مدعوماً بالكامل.

### تشخيص إضافي (لا يكتم الخطأ)
- `lib/main.dart`: `runZonedGuarded` + `FlutterError.onError` + `PlatformDispatcher.onError`
  تطبع `NOVA_CRASH*` في logcat **ثم** تترك السلوك الافتراضي كما هو.

### الحدود (بصراحة)
- **لم يُختبر على جهاز ARM64 حقيقي**؛ لا يتوفر جهاز في هذه البيئة. المحاكي لا يعيد إنتاج
  الانهيار الأصلي (نسخة ما قبل الإصلاح كانت تعمل عليه أيضاً)، لذلك لا يمكن الجزم بأن
  إيقاف Impeller هو السبب الجذري المؤكد — هو الإجراء المدعوم بأقوى الأدلة المتاحة.
- إذا استمر الإغلاق على الهاتف، فالمطلوب دليل من الجهاز نفسه:
  `adb logcat -b crash` أو `adb logcat | grep -E "NovaCraft|NOVA_CRASH|libflutter"`،
  أو ملف `files/last_crash.txt` من بيانات التطبيق. حينها يمكن تحديد السبب النهائي بدقة.
